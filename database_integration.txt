4. PHASE 2 - GRAPH AND SCHEMA DESIGN
======================================================================

4.1 Graph Name

TraceGuardGraph

4.2 Primary Vertex

PaymentTransaction

The PaymentTransaction vertex represents an individual financial
transaction.

The transaction entity is the primary data object used for risk analysis
and fraud investigation.

4.3 Transaction attributes

The graph model includes transaction-oriented information such as:

-   Transaction ID
-   Transaction amount
-   Timestamp
-   Risk indicators
-   Other attributes required for investigation and analytics

The exact schema should always be obtained from the live TigerGraph
workspace rather than hard-coded from this document.

Recommended backend workflow:

1.  Connect securely to TigerGraph.
2.  Run schema discovery.
3.  Inspect vertex and edge definitions.
4.  Confirm attribute names and data types.
5.  Generate/validate backend models.
6.  Execute test GSQL queries.

4.4 Graph relationships

TraceGuard AI is designed around relationships between entities.

Depending on the finalized schema, relationships can represent
connections such as:

Transaction -> Account Transaction -> Customer Transaction -> Device
Transaction -> IP Address Transaction -> Transaction

The production implementation must use the relationships that actually
exist in TraceGuardGraph. Do not assume an edge type that has not been
created.

======================================================================

5.1 Source Data

Transaction datasets were prepared for ingestion into the TigerGraph

5.2 Target-to-source mapping

Target-to-source mapping rules were configured for the
PaymentTransaction vertex.

The mapping process connects source dataset columns to the attributes

Example conceptual mapping:

Source Column -> TigerGraph Attribute

A TigerGraph data loading job was created, configured, and published.

Verification should include:

-   Checking transaction IDs.
-   Checking transaction amounts.
-   Checking timestamps.
-   Checking risk-related attributes.
-   Checking relationships/edges where applicable.
-   Comparing loaded counts against the source dataset.

11. QUERY DESIGN
======================================================================

Queries should be designed around investigation use cases rather than
simply exposing raw database data.

Examples of useful query categories:

A. Transaction lookup - Find a transaction by ID.

B. Transaction history - Retrieve transactions associated with an
entity.

C. Relationship traversal - Identify connected accounts, devices, IPs,
or other entities.

D. Risk analysis - Retrieve transaction attributes required by the risk
engine.

E. Investigation context - Retrieve graph evidence needed by the AI
agent and GraphRAG layer.

F. Case analysis - Retrieve connected evidence for an investigation
case.

Queries should return only the information required by the API layer.

======================================================================
13. ERROR HANDLING
======================================================================

The backend should handle at least the following cases:

Authentication failure - Return an appropriate server-side error. - Do
not expose the secret or token.

TigerGraph unavailable - Return a controlled service-unavailable
response. - Log the failure without credentials.

Invalid graph name - Fail configuration validation early.

Invalid query - Log the query identifier and error details. - Do not
expose internal credentials.

Empty result - Return a valid empty response rather than crashing.

Timeout - Apply reasonable request timeouts. - Return a controlled
timeout response.

Schema mismatch - Detect unexpected attributes/types. - Log the mismatch
for investigation.

14. SECURITY REQUIREMENTS
======================================================================

Security is critical because TraceGuard AI processes potentially
sensitive transaction and fraud-investigation data.

Required practices:

1.  Never commit TigerGraph secret keys.
2.  Never place database credentials in frontend code.
3.  Never expose secrets in API responses.
4.  Use HTTPS for external communication.
5.  Store credentials in environment variables or a secure secret store.
6.  Rotate compromised credentials immediately.
7.  Restrict production access using least privilege.
8.  Avoid logging authentication tokens.
9.  Sanitize application logs.
10. Validate all incoming API requests.
11. Use authentication/authorization for backend endpoints.
12. Avoid exposing raw database errors to end users.

IMPORTANT: Any credential included in an earlier project note, chat
message, screenshot, repository, or public document should be considered
exposed. Rotate it before using the system in production.
